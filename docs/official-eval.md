# 官方评测：把黑米放到公开的尺子上量

这是一条单独运行的命令。它用公开的标准评测题，给黑米每个阶段的检查点打分，再放一个 GPT-2 small 在旁边做对照，让你看到黑米大概在什么水平。窗口的第五个区域"官方评测"会显示结果。

它和训练里自带的评测（`evaluate.py`、验证损失）是两回事：自带评测回答"这一级比上一级好了多少"，这里回答"放在另一个模型旁边是什么水平"。训练里的评测不受影响。

## 怎么运行

先装一次额外依赖（只有这条命令要用，训练和窗口不需要）：

```
uv pip install -e ".[official]"
```

没装就运行，命令会打印上面这条安装命令，然后退出，什么也不会评。

之后每次只用下面三种：

```
python official_eval.py --run heimi
python official_eval.py --run heimi --ckpt stage1_final.pt --limit 50 --code-limit 50
python official_eval.py --reference gpt2
```

1. 第一条：评 `runs/heimi/ckpt/` 下每个还没评过的 `*_final.pt`。每训完一个阶段，训练停下来后运行一次它，表里就多一行。评过的会跳过：再运行一次，会提示"没有待评测的检查点"，什么也不做，这是正常的。
2. 第二条：只评指定的检查点，并且只评一小部分题，用来快速试通。试跑的结果在窗口里会标"（抽样）"，不能和全量结果放在一起比。
3. 第三条：重新评 GPT-2 small，结果写进 `docs/official/reference.json`。这个文件已经在仓库里了，只有想重测时才需要运行。

### 选项

| 选项 | 作用 |
|---|---|
| `--run 名字` | 评 `runs/` 下这个 run 的检查点 |
| `--reference gpt2` | 评参照模型 GPT-2 small，写参照文件 |
| `--ckpt 文件名` | 只评这个检查点，可以重复写几次 |
| `--device cuda` 或 `cpu` | 用显卡还是处理器，默认有显卡就用显卡 |
| `--limit N` | 三个标准任务每个子任务最多评 N 条，默认全部。必须是 1 以上的整数 |
| `--code-limit N` | 代码评测抽 N 条，默认 500。必须是 1 以上的整数 |
| `--code-all` | 代码评测用全部题目。黑米每写一个新 token（模型读写文字的最小单位，可以是一个词、半个词或一串空白）都要把前面的全部文字重新算一遍（没有缓存），所以生成很慢，103M 的模型要跑好几个小时 |
| `--skip-code` | 不跑代码评测 |
| `--force` | 已经评过的也重评。评参照模型时，允许用不够完整的结果覆盖文件里更完整的结果 |
| `--allow-busy-gpu` | 显卡已被占用也照样评（见"训练在跑的时候"） |
| `--runs`、`--data-dir`、`--reference-out` | 改 run 目录、评测数据目录、参照文件的位置，一般不用动 |

### 要多久

下面是在这台机器上（RTX 5080 16 GB）量出来的时间，全部用显卡：

| 命令 | 耗时 |
|---|---|
| 评 GPT-2 小样本试跑（第一次，含下载 GPT-2 约 550 MB 和两份代码评测数据约 158 MB） | 4 分 6 秒 |
| 评一个黑米检查点小样本试跑 | 1 分 31 秒 |
| 评 GPT-2 全量 | 15 分 52 秒（上午）；16 分 51 秒（下午重测） |
| 评黑米四个检查点全量 | 上午共 30 分 37 秒：stage0 6 分 32 秒，stage1 7 分 47 秒，stage2 8 分 22 秒，task 7 分 54 秒。下午重测共 33 分 14 秒：stage0 7 分 57 秒，stage1 7 分 16 秒，stage2 8 分 22 秒，task 9 分 36 秒 |

也就是说，之后每训完一个阶段，评一个检查点大约 6 分半到 9 分半（代码评测按默认的 500 条算）。

## 每个数字是什么

先讲两个词。**随机水平**是"闭着眼乱猜能得多少分"，模型的分数要和它比才知道有没有学到东西；表里写"—"的列没有给出随机水平，主要看和 GPT-2 那一行的差距。**方向**是数字越大越好，还是越小越好。

| 列 | 它在量什么 | 随机水平 | 方向 |
|---|---|---|---|
| BLiMP | 给一对句子，一句语法对、一句语法错，看模型是不是觉得对的那句更通顺。分数是选对的比例 | 0.5 | 越高越好 |
| HellaSwag | 给一段开头和四个结尾，选最合理的结尾。表里 `acc` 是直接比概率，`acc_norm` 是把长短不同的结尾按长度修正后再比，窗口只显示 `acc_norm` | 0.25 | 越高越好 |
| WikiText bits/byte | 让模型"读"一批维基百科文章，看它平均每个字节的内容让它多意外。意外得越少，说明预测得越准。它按原文的字节数算，所以词表大小不同的两个模型也能直接比 | — | 越低越好 |
| WikiText word perplexity | 同样的实验，换成按词数算的"困惑度"，可以理解为模型每个词面前平均在几个候选里犹豫。同样不受词表影响 | — | 越低越好 |
| RepoBench EM | 给一段 Python 文件的开头，让模型写下一行，和标准答案一字不差才算对。EM 是这样答对的比例 | — | 越高越好 |
| RepoBench ES | 同一道题，不要求一字不差，按两行文字有多像打分，满分 100 | — | 越高越好 |
| 单行填空（FIM） | 给一段代码的前半和后半，让模型补中间一行，一字不差才算对。FIM 是"填中间"的意思。只有学过填空格式的模型才做得了 | — | 越高越好 |
| 单行填空（仅前缀） | 同样的题，但只给前半，让模型接着往下写一行 | — | 越高越好 |

EM、单行填空的数字是答对题数占抽样题数的比例（0 到 1），窗口里显示成百分数。

## 哪些是官方指标，哪些不是

- **BLiMP、HellaSwag、WikiText 是官方的。** 它们交给公开的评测框架 lm-evaluation-harness（版本 0.4.13）原样运行，题目、提示和打分都是别人定的。
- **RepoBench 是"大体官方"。** 数据、提示的拼法、取答案行的办法都用官方的，但有五处不同（第 5 处是 2026-11-21 下午加的）：
  1. 只用 `in_file` 这一部分题（提示里只放当前这一个文件）。官方的另一种设置要把别的文件的片段也塞进去，黑米的上下文只有 1,024 个 token，放不下。
  2. 解码用"贪心"（每一步都选概率最大的那个），而不是官方的随机采样（temperature 0.2，top_p 0.95，这是控制模型选词有多随机的两个设置）。贪心每次结果相同，可以复现。
  3. 只抽 500 题，不是全部 7,910 题。抽样的种子固定为 1337，每次抽到同样的题。
  4. ES 用标准库自己重写了官方 `fuzzywuzzy` 的打分公式，没有用那个库。
  5. 提示结尾的那个换行不直接喂给模型，而是让模型自己写出来。官方是原样喂进去。为什么改、怎么改，见下面"代码题的出题方式"一节。
- **单行填空不是官方指标。** 官方对 HumanEval 填空的打分是 pass@1：把模型写的代码拼回去，真的运行单元测试。这个项目任何时候都不运行模型写出来的代码，所以只做"和标准答案一字不差"。补出来的行和标准答案一样，拼回去必然通过测试，所以一字不差的比例大体上是 pass@1 的下界（真实的 pass@1 一般只会更高）。有两处要知道：比较时不看行首的缩进，缩进写错、内容写对的行在这里也算对，而真的运行多半会出错，所以严格说它不是下界；只取模型写的第一行，模型先空一行再写出正确内容的，这里算错。窗口表格下面的说明里也写着这两列不是官方的 pass@1。GPT-2 没学过填空，只有"仅前缀"一列。

## 为什么只和表里的 GPT-2 比

表里第一行的 GPT-2 small 是在**同一台机器**上、用**同一版本的框架**、**同样的题数**、**同样的代码**测的。黑米的数字只能和这一行比。（代码列请看"第二次实测"的表。第一次实测的代码列用的是旧出题方式，压低了黑米的数字，已经被取代。）

不要拿它们去对论文或排行榜上的数字，原因有三个：别人的设置和这里不一样（RepoBench 一节讲了五处不同）；这里打分用 float32 精度、解码用贪心；而且抽样的结果和全量的结果也不能互相比（窗口会把这样的行标出来，见下面"窗口"一节）。

选 GPT-2 small 是因为它的大小（非嵌入参数 85M）和黑米 stage2 的 103M 在同一个量级。

## 训练在跑的时候怎么办

训练占着显卡时，这条命令不会开始，会说明显存已经用了多少，并给三条出路：等训练停下来再评；加 `--device cpu` 用处理器评（慢，但不影响训练）；确认显存够用就加 `--allow-busy-gpu`。原因和其他运行时的注意事项见最后一节的第 4 条。

## 窗口里怎么看

窗口的"官方评测"区域第一行是 GPT-2（参照），后面每个检查点一行。行名后面可能有标记，意思见 [`dashboard.md`](dashboard.md)。

## 代码题的出题方式（2026-11-21 下午改过一次）

两个代码评测（RepoBench、单行填空）现在用的是修正后的出题方式，记录里写作 `code_method: "healed"`。第一次实测用的是旧方式（记作 `"plain"`，那时的记录里没有这一项）。两种方式的代码成绩不能放在一起比；三个标准任务不受影响。

**旧方式哪里不对。** 两个评测的提示都停在一个换行后面，等模型写下一行。黑米的分词器（把文字切成 token 的工具）会把"换行加后面的缩进"合成一个 token，所以"单独一个换行 token，后面却接着带缩进的代码"这种切法，在它的训练数据里几乎不出现。模型没见过这种开头，就接着写顶格的内容，评测只取第一行，答案成了空的。这是出题方式和黑米的分词习惯对不上，不是黑米不会写。GPT-2 的分词器不合并换行和缩进，没有这个问题。

**新方式怎么做。**

- 提示照常切成 token。最后一个 token 如果只是空白（换行、空格、制表符），就不放进提示，改由模型自己写。
- 模型写的第一个 token，只能在"文字以那段空白开头"的 token 里选，选它打分最高的那个。它可以原样写回同一个 token，那样后面的一切和旧方式一模一样；也可以选一个更长的，比如黑米直接写出"换行加 4 个空格"这一个 token。之后照常一步步选概率最大的。
- 模型知道的信息和原来一样：那段空白是什么是定死的，它改不了。变的只是这一个 token 在哪里结束，由模型按自己的习惯定。
- 交给计分的，仍然是接在原提示后面的那段文字。取哪一行、怎么算对、贪心解码、最多 64 个新 token（重写的那一个不占额度）、提示从哪里截、抽哪 500 题，都没变。
- 黑米和 GPT-2 用同一套规则。
- 单行填空还多一处：待填那一行行末的换行，原数据算在答案里，现在算在后缀开头。整篇文字一个字符都没变，只是后缀改成从一串空白的起点切开，和黑米训练时见到的切法一致。这一处只影响黑米的 FIM 列（GPT-2 不看后缀）。

**核对过的数字**（只读脚本，不跑模型）。500 道抽样题里，"正确答案按模型自己的分词习惯写出来"在规则允许范围内的题数：

| | 黑米，旧方式 | 黑米，新方式 | GPT-2，旧方式 | GPT-2，新方式 |
|---|---|---|---|---|
| 单行填空，提示这一侧 | 0 | 498 | 500 | 500 |
| RepoBench，提示这一侧 | 47 | 500 | 500 | 500 |
| 单行填空，后缀这一侧（只有黑米的 FIM 用） | 73 | 490 | — | — |

1,000 道抽样题的提示，最后一个 token 全都是空白（两个模型都是）。全部 1,033 道填空题的答案都是以换行结尾的一整行（读数据时会检查，不符合就报错）。黑米剩下的 2 道和 10 道，是提示或答案的行末自己带着多余的空格，规则没有去动它们。

**对已有记录的影响。** 旧方式留下的记录不算"评过"：再运行 `python official_eval.py --run heimi`，带代码评测的检查点会用新方式重评一遍，不用加 `--force`。窗口只在一行的出题方式和参照行相同时才把它们并排比，否则标"设置与参照不同"。

### 和第一次比，变了什么

- **三个标准任务一点没变。** 两个模型、每个检查点的数字都和第一次逐位相同。这说明评测可以复现，也说明这次改动没有碰到它们。"第一次实测"里"黑米现在在什么位置"关于这三项的话照旧成立。
- **GPT-2 的代码列几乎没变**：EM 0.044 还是 0.044，ES 从 32.80 到 32.41，填空 0.026 还是 0.026。这是事先写下的检验：GPT-2 的分词本来就对得上，新规则允许它把那个换行原样写回。实际数下来，500 道 RepoBench 题里它有 461 道原样写回，500 道填空题里有 498 道。
- **黑米的代码列大幅上升**（箭头左边是第一次，右边是这一次）：

| 阶段 | RepoBench EM | RepoBench ES | 单行填空（FIM） | 单行填空（仅前缀） |
|---|---|---|---|---|
| stage0 | 0.000 → 0.010 | 15.00 → 32.67 | 0.000 → 0.006 | 0.000 → 0.026 |
| stage1 | 0.010 → 0.054 | 19.12 → 49.30 | 0.000 → 0.000 | 0.002 → 0.058 |
| stage2 | 0.024 → 0.098 | 22.36 → 55.00 | 0.002 → 0.000 | 0.002 → 0.066 |
| task | 0.030 → 0.100 | 26.46 → 55.12 | 0.002 → 0.028 | 0.006 → 0.096 |

黑米很少把换行原样写回：四个检查点在 500 道 RepoBench 题里只有 34 到 47 道，在 500 道填空题里只有 1 到 5 道，其余都是连缩进一起写成一个 token。这和"旧方式的切法它没见过"的判断对得上。

### 现在代码列怎么读

- 从 stage1（26M）起，黑米在 RepoBench 上高于这里测的 GPT-2 small，按表里的规则在仅前缀填空上也高于它。stage0（13M）和 GPT-2 大致持平：ES 是 32.67 对 32.41，填空都是 0.026，EM 是 0.010 对 0.044，低一些。填空一列领先多少和取行规则有关，见下面"要小心的地方"第 3 条。
- **这不等于"黑米比 GPT-2 强"。** 三项标准任务上 GPT-2 仍然全部领先。代码上领先有现成的解释：黑米的训练数据里有大量 GitHub 上的代码（`codeparrot/github-code-clean`），GPT-2 的训练文本是网页文章。这两道题考的正是黑米练得多的东西。
- 每长大一级，RepoBench 都在升。stage2 和 task 的 RepoBench 基本一样（EM 0.098 对 0.100，ES 55.00 对 55.12）。第一次实测里 task 看着比 stage2 高一截，现在看主要是旧出题方式造成的。
- 500 道题的抽样误差不小：答对率在 5% 到 10% 时，一个标准误大约是 1 到 1.3 个百分点。相差一两个百分点的两个数不要分高下。
- FIM 一列只有 task 阶段有意义，前三个阶段没学过填空格式，接近 0 是应该的。task 阶段 FIM 是 0.028，仅前缀是 0.096：**看了后缀反而更差。** 学过填空的模型应该是看了后缀更好。这件事没有查清：可能是填空训练没达到预期，也可能是评测的 FIM 提示还有别的地方和训练时不一样。查清之前，不要用 FIM 这一列下结论。

### 另抽 500 题的复核

出题规则是在上午的诊断之后定的，那次诊断看过这 500 题里的前 100 题（见下面"要小心的地方"第 1 条）。为了确认上面的数字不是挑题挑出来的，又从官方那 500 题**以外**的题里另抽了 500 题（种子 2026；RepoBench 从剩下的 7,410 题里抽，填空从剩下的 533 题里抽），用完全相同的代码再算一遍。这是复核，不是官方记录，不进窗口的表：

| 模型 | RepoBench EM | RepoBench ES | 单行填空（FIM） | 单行填空（仅前缀） |
|---|---|---|---|---|
| GPT-2 small | 0.020 | 31.48 | — | 0.026 |
| stage0 | 0.006 | 33.16 | 0.010 | 0.030 |
| stage1 | 0.034 | 49.08 | 0.000 | 0.056 |
| stage2 | 0.070 | 54.53 | 0.000 | 0.098 |

### 要小心的地方（六条）

**1. 这不是一次盲测，规则中途还改过一次。**

规则是在全量评测之前定下并提交的，跑出来的数字不管好坏都照实记。但有三件事要照实说：

- 上午那次 100 题的诊断用的是相近的做法，已经看到黑米的数字会升。规则是在那之后定的，那 100 题也在官方的 500 题里。所以才有上一小节的复核。
- 规则改过一次。第一版（提交 `b26c17d`）是把提示结尾的整串空白都交给模型，分几步写回来。小样本试跑后看模型实际写了什么，发现在以空行结尾的提示上（500 道填空题里有 99 道），GPT-2 会被逼着写出两个单独的换行 token，而在这种位置它自己的分词器只会写一个"空一行"的 token。这等于把同一类毛病转给了 GPT-2。于是在跑全量之前改成现在这版（提交 `79d15a5`）。改之前只看过 20 道试跑题的输出，没有看过任何全量成绩；改动的方向是照顾 GPT-2。
- `runs/heimi/official.jsonl` 里有一条 16:16 的抽样记录（task，只评 20 题）是第一版规则跑的，标签同样是 `healed`。它不会显示在表里，抽样记录排在全量记录后面。

**2. 黑米可能见过一部分考题，GPT-2 不可能见过。**

和第一次实测的第 2 条是同一件事，现在更要紧，因为填空一列黑米已经高于 GPT-2。HumanEval 的题目和答案 2021 年起就公开在 GitHub 上，黑米的代码数据正是从 GitHub 来的；RepoBench 的题也取自 GitHub 上的仓库。重合检查**没有做过**。做之前，黑米的填空和 RepoBench 数字相对 GPT-2 可能偏好看，偏多少不知道。

**3. 填空这一列的领先幅度，和"取哪一行、看不看缩进"有关。**

表里的规则是：只取模型写的第一行，比较时不看行首缩进。这两条从第一次实测起就是这样，这次没有改。它们对两个模型的影响不一样，所以在官方那 500 道题上按四种读法各数了一遍（仅前缀模式；这是另外量的，不是官方记录）：

| 读法 | GPT-2 small | stage2 | task |
|---|---|---|---|
| 表里的规则：只取第一行，不看缩进 | 13 道（0.026） | 33 道（0.066） | 48 道（0.096） |
| 跳过开头的空行，不看缩进 | 28 道（0.056） | 34 道（0.068） | 50 道（0.100） |
| 只取第一行，缩进也要对 | 8 道（0.016） | 30 道（0.060） | 44 道（0.088） |
| 跳过开头的空行，缩进也要对 | 9 道（0.018） | 31 道（0.062） | 46 道（0.092） |

- GPT-2 在 500 道题里有 436 道是先空一行再写的（stage2 是 5 道，task 是 8 道）。"只取第一行"把这些全算错，所以表里的 0.026 对 GPT-2 偏严。跳过空行，它是 0.056，和 stage2 的 0.068 分不出高下。
- 反过来，"不看缩进"对 GPT-2 有利，它常写顶格的代码。要求缩进也对（更接近"拼回去能不能运行"），它只有 0.016 到 0.018。
- 四种读法下，task 阶段都明显高于 GPT-2。stage2 是否领先、领先多少，取决于读法。stage0、stage1 没有另外量。

**4. 重写的那个 token 不占 64 个新 token 的额度。**

黑米把换行连缩进一起写时，等于缩进没花额度；旧方式下它得另花一个 token 写缩进。GPT-2 没有这样的 token。差别最多是一个 token，方向对黑米略有利。

**5. task 阶段的 FIM 低于仅前缀，原因没查清。** 见上面"现在代码列怎么读"的最后一条。

**6. 哪些数字是官方的、运行时要注意什么**，和第一次实测的第 3、4 条相同，见下一节。代码两项现在比官方做法多一处不同（提示最后那个空白 token 交给模型重写）。

### 要小心的地方（四条）

**1. 代码的四列低估了黑米（先看这条）。**

黑米的分词方式（把文字切成 token 的方式）会把"换行加后面的缩进"合成一个 token（例如"换行加 7 个空格"是一个 token）。可是两个代码评测都把一个以光秃秃的换行结尾的提示交给模型，等它写下一行带缩进的代码。"光秃秃的换行后面接缩进"这种写法从没在黑米的训练数据里出现过，所以模型在它后面写的是顶格（不带缩进、从行首开始写）的内容（多半又是一个换行，然后一个新的 `def`），而评测只取第一个换行之前的文字，于是答案成了空的。

证据来自只读的诊断脚本（没有运行任何模型写的代码）：把提示和"提示加标准答案"分别分词，在边界之前的 token 完全一样的，500 道抽样填空题里是 0 道，500 道抽样 RepoBench 题里是 47 道（这 500 道 RepoBench 的标准答案里 454 道是带缩进的）。在 60 道填空题上，task 阶段的模型有 53 道（FIM 模式）和 34 道（仅前缀模式）直接答了空字符串。

另外做了一个**诊断**，方法和上面的表不同，不是官方记录，也不在表里：把提示末尾的换行拿掉，让模型自己写出"换行加缩进"那个 token，再取第一行非空内容。只在同样抽样的前 100 题上做：

| 阶段 | 项目 | 表里的方法 | 诊断的方法 |
|---|---|---|---|
| task | 填空（仅前缀）答对 | 2 / 100 | 9 / 100 |
| task | RepoBench EM | 3 / 100 | 10 / 100 |
| task | RepoBench ES | 26.4 | 49.6 |
| stage2 | 填空（仅前缀）答对 | 1 / 100 | 7 / 100 |
| stage2 | RepoBench EM | 3 / 100 | 13 / 100 |
| stage2 | RepoBench ES | 25.7 | 51.4 |

这说明表里黑米的代码数字被评测方式压低了很多。当天下午做了后续：查了 GPT-2 的分词器（它没有这个毛病），把修正后的出题方式用在两个模型上，两边都重新评了一遍，结果见"第二次实测"。还有一件没弄明白的事，重测后仍然在：task 阶段的 FIM 模式比仅前缀模式差，项目自己的"样本墙"里 task 阶段也有"（什么都没写）"。task 阶段的填空训练是不是按预期起了作用，没有调查。

结论：三个标准任务的列可以信；这张表里的四个代码列，对黑米来说只能当作"至少有这么多"，不要据此得出"黑米写代码不如 GPT-2"。

**2. 黑米可能见过一部分考题，GPT-2 不可能见过。**

黑米的通用文本是 `HuggingFaceFW/fineweb-edu`（网页），代码来自 `codeparrot/github-code-clean`（GitHub 上的代码，见 `docs/data/report.md`）。WikiText-2 是维基百科的文章，HumanEval 的题目 2021 年起就公开在 GitHub 上，所以这两样都可能混在黑米的训练数据里。GPT-2（2019 年）用的 WebText 数据里特意去掉了维基百科，而且它比 HumanEval 还早。

这件事**没有量过**，没有做过重合检查。在检查之前，黑米的 WikiText 和单行填空数字相对 GPT-2 可能偏好看。程度不知道，这里不估。

**3. 哪些数字是官方的。**

BLiMP、HellaSwag、WikiText 是官方评测，框架原样运行。RepoBench 是官方的数据和提示，但只用 `in_file`、贪心解码、抽 500 题、ES 是自己重写的公式。单行填空是一字不差的比例，不是官方的 pass@1，只是它的下界，因为这里从不运行模型写出来的代码。这些数字只能和表里的 GPT-2 比，不能和论文、排行榜比。

**4. 运行时的注意事项，以及一个没核实的东西。**

- 训练在跑时命令拒绝在显卡上开始，是因为 Windows 上显存不够不会报错，而是悄悄挤到系统内存里，评测和训练两边都会慢得像爬。三条出路见上面"训练在跑的时候怎么办"。评 GPT-2 全量时显存最高用到约 15.4 GB（显卡共 16.3 GB），已经贴着那条线，所以评参照时不要同时开游戏或训练。
- 记录按检查点的**文件名**记。你重新训练出一个同名的检查点，命令会以为评过了而跳过，要加 `--force` 才会重评。
- 只评一部分题的 GPT-2（`--reference gpt2 --limit N`）不会覆盖参照文件里已有的更完整结果，命令会拒绝。想覆盖加 `--force`，想另存加 `--reference-out 别的路径`。
- 设计说明里给 GPT-2 标的合理范围（BLiMP 0.75 以上、HellaSwag `acc_norm` 在 0.28 到 0.34、WikiText word perplexity 在 30 到 45）是凭记忆写的，没有逐一核实，只用来发现明显的环境错误，不是验收线。这次三个数都落在范围里（0.8215、0.3114、37.37）。
