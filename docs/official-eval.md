# 官方评测：把黑米放到公开的尺子上量

这是一条单独运行的命令。它用公开的标准评测题，给黑米每个阶段的检查点打分，再放一个 GPT-2 small 在旁边做对照，让你看到黑米大概在什么水平。窗口的第五个区域"官方评测"会显示结果。

它和训练里自带的评测（`evaluate.py`、验证损失）是两回事：自带评测回答"这一级比上一级好了多少"，这里回答"放在另一个模型旁边是什么水平"。训练里的评测不受影响。

## 怎么运行

先装一次额外依赖（只有这条命令要用，训练和窗口不需要）：

```
uv pip install -e ".[official]"
```

没装就运行，命令会打印上面这条安装命令，然后退出，什么也不会评。

之后每次只用下面三种：

```
python official_eval.py --run heimi
python official_eval.py --run heimi --ckpt stage1_final.pt --limit 50 --code-limit 50
python official_eval.py --reference gpt2
```

1. 第一条：评 `runs/heimi/ckpt/` 下每个还没评过的 `*_final.pt`。每训完一个阶段，训练停下来后运行一次它，表里就多一行。评过的会跳过：再运行一次，会提示"没有待评测的检查点"，什么也不做，这是正常的。
2. 第二条：只评指定的检查点，并且只评一小部分题，用来快速试通。试跑的结果在窗口里会标"（抽样）"，不能和全量结果放在一起比。
3. 第三条：重新评 GPT-2 small，结果写进 `docs/official/reference.json`。这个文件已经在仓库里了，只有想重测时才需要运行。

### 选项

| 选项 | 作用 |
|---|---|
| `--run 名字` | 评 `runs/` 下这个 run 的检查点 |
| `--reference gpt2` | 评参照模型 GPT-2 small，写参照文件 |
| `--ckpt 文件名` | 只评这个检查点，可以重复写几次 |
| `--device cuda` 或 `cpu` | 用显卡还是处理器，默认有显卡就用显卡 |
| `--limit N` | 三个标准任务每个子任务最多评 N 条，默认全部。必须是 1 以上的整数 |
| `--code-limit N` | 代码评测抽 N 条，默认 500。必须是 1 以上的整数 |
| `--code-all` | 代码评测用全部题目。黑米每写一个新 token（模型读写文字的最小单位，可以是一个词、半个词或一串空白）都要把前面的全部文字重新算一遍（没有缓存），所以生成很慢，103M 的模型要跑好几个小时 |
| `--skip-code` | 不跑代码评测 |
| `--force` | 已经评过的也重评。评参照模型时，允许用不够完整的结果覆盖文件里更完整的结果 |
| `--allow-busy-gpu` | 显卡已被占用也照样评（见"训练在跑的时候"） |
| `--runs`、`--data-dir`、`--reference-out` | 改 run 目录、评测数据目录、参照文件的位置，一般不用动 |

### 要多久

下面是在这台机器上（RTX 5080 16 GB）量出来的时间，全部用显卡：

| 命令 | 耗时 |
|---|---|
| 评 GPT-2 小样本试跑（第一次，含下载 GPT-2 约 550 MB 和两份代码评测数据约 158 MB） | 4 分 6 秒 |
| 评一个黑米检查点小样本试跑 | 1 分 31 秒 |
| 评 GPT-2 全量 | 15 分 52 秒 |
| 评黑米四个检查点全量 | 共 30 分 37 秒：stage0 6 分 32 秒，stage1 7 分 47 秒，stage2 8 分 22 秒，task 7 分 54 秒 |

也就是说，之后每训完一个阶段，评一个检查点大约 6 分半到 8 分半（代码评测按默认的 500 条算）。

## 每个数字是什么

先讲两个词。**随机水平**是"闭着眼乱猜能得多少分"，模型的分数要和它比才知道有没有学到东西；表里写"—"的列没有给出随机水平，主要看和 GPT-2 那一行的差距。**方向**是数字越大越好，还是越小越好。

| 列 | 它在量什么 | 随机水平 | 方向 |
|---|---|---|---|
| BLiMP | 给一对句子，一句语法对、一句语法错，看模型是不是觉得对的那句更通顺。分数是选对的比例 | 0.5 | 越高越好 |
| HellaSwag | 给一段开头和四个结尾，选最合理的结尾。表里 `acc` 是直接比概率，`acc_norm` 是把长短不同的结尾按长度修正后再比，窗口只显示 `acc_norm` | 0.25 | 越高越好 |
| WikiText bits/byte | 让模型"读"一批维基百科文章，看它平均每个字节的内容让它多意外。意外得越少，说明预测得越准。它按原文的字节数算，所以词表大小不同的两个模型也能直接比 | — | 越低越好 |
| WikiText word perplexity | 同样的实验，换成按词数算的"困惑度"，可以理解为模型每个词面前平均在几个候选里犹豫。同样不受词表影响 | — | 越低越好 |
| RepoBench EM | 给一段 Python 文件的开头，让模型写下一行，和标准答案一字不差才算对。EM 是这样答对的比例 | — | 越高越好 |
| RepoBench ES | 同一道题，不要求一字不差，按两行文字有多像打分，满分 100 | — | 越高越好 |
| 单行填空（FIM） | 给一段代码的前半和后半，让模型补中间一行，一字不差才算对。FIM 是"填中间"的意思。只有学过填空格式的模型才做得了 | — | 越高越好 |
| 单行填空（仅前缀） | 同样的题，但只给前半，让模型接着往下写一行 | — | 越高越好 |

EM、单行填空的数字是答对题数占抽样题数的比例（0 到 1），窗口里显示成百分数。

## 哪些是官方指标，哪些不是

- **BLiMP、HellaSwag、WikiText 是官方的。** 它们交给公开的评测框架 lm-evaluation-harness（版本 0.4.13）原样运行，题目、提示和打分都是别人定的。
- **RepoBench 是"大体官方"。** 数据、提示的拼法、取答案行的办法都用官方的，但有四处不同：
  1. 只用 `in_file` 这一部分题（提示里只放当前这一个文件）。官方的另一种设置要把别的文件的片段也塞进去，黑米的上下文只有 1,024 个 token，放不下。
  2. 解码用"贪心"（每一步都选概率最大的那个），而不是官方的随机采样（temperature 0.2，top_p 0.95，这是控制模型选词有多随机的两个设置）。贪心每次结果相同，可以复现。
  3. 只抽 500 题，不是全部 7,910 题。抽样的种子固定为 1337，每次抽到同样的题。
  4. ES 用标准库自己重写了官方 `fuzzywuzzy` 的打分公式，没有用那个库。
- **单行填空不是官方指标。** 官方对 HumanEval 填空的打分是 pass@1：把模型写的代码拼回去，真的运行单元测试。这个项目任何时候都不运行模型写出来的代码，所以只做"和标准答案一字不差"。补出来的行和标准答案一样，拼回去必然通过测试，所以一字不差的比例是 pass@1 的下界（真实的 pass@1 只会更高）。窗口表格下面的说明里也写着这两列不是官方的 pass@1。GPT-2 没学过填空，只有"仅前缀"一列。

## 为什么只和表里的 GPT-2 比

表里第一行的 GPT-2 small 是在**同一台机器**上、用**同一版本的框架**、**同样的题数**、**同样的代码**测的。黑米的数字只能和这一行比。（目前四个代码列是例外：评测方式压低了黑米的数字，见"首次实测"一节"要小心的地方"的第 1 条，在那之前不要信这四列。）

不要拿它们去对论文或排行榜上的数字，原因有三个：别人的设置和这里不一样（RepoBench 一节讲了四处不同）；这里打分用 float32 精度、解码用贪心；而且抽样的结果和全量的结果也不能互相比（窗口会把这样的行标出来，见下面"窗口"一节）。

选 GPT-2 small 是因为它的大小（非嵌入参数 85M）和黑米 stage2 的 103M 在同一个量级。

## 训练在跑的时候怎么办

训练占着显卡时，这条命令不会开始，会说明显存已经用了多少，并给三条出路：等训练停下来再评；加 `--device cpu` 用处理器评（慢，但不影响训练）；确认显存够用就加 `--allow-busy-gpu`。原因和其他运行时的注意事项见最后一节的第 4 条。

## 窗口里怎么看

窗口的"官方评测"区域第一行是 GPT-2（参照），后面每个检查点一行。行名后面可能有标记，意思见 [`dashboard.md`](dashboard.md)。

**读表之前先看下面"要小心的地方"，尤其是第一条：右边四个代码列在这张表里不能当结论用。**

### 黑米现在在什么位置

只说三个标准任务（BLiMP、HellaSwag、WikiText）：

- 从 stage0 到 stage2，每长大一级，三项都变好：BLiMP 从 0.610 升到 0.689，再到 0.755；WikiText bits/byte 从 1.69 降到 1.31，再到 1.16。
- stage2（103M）的 BLiMP 是 0.755，GPT-2 是 0.822，已经接近但没追上。WikiText bits/byte 是 1.157，GPT-2 是 0.977，差距还在。
- HellaSwag 在每个阶段都只比随机水平 0.25 高一点点：`acc_norm` 从 0.257 升到 0.283（GPT-2 是 0.311）。
- stage0 的 BLiMP（0.610）比随机水平 0.5 高，但 HellaSwag（0.257）只有一点点高于随机。
- task 阶段在三项标准任务上比 stage2 略低（BLiMP 0.7438 对 0.7553；bits/byte 1.1731 对 1.1568），在 RepoBench 上略高（EM 0.030 对 0.024，ES 26.46 对 22.36）。task 阶段是在 stage2 基础上，把训练数据换成 80% 代码、20% 网页，并且一半的代码窗口改写成填空格式（见主设计文档第 6、11 节）。这个小差别的原因没有查过，这里不猜。

### 要小心的地方（四条）

**1. 代码的四列低估了黑米（先看这条）。**

黑米的分词方式（把文字切成 token 的方式）会把"换行加后面的缩进"合成一个 token（例如"换行加 7 个空格"是一个 token）。可是两个代码评测都把一个以光秃秃的换行结尾的提示交给模型，等它写下一行带缩进的代码。"光秃秃的换行后面接缩进"这种写法从没在黑米的训练数据里出现过，所以模型在它后面写的是顶格（不带缩进、从行首开始写）的内容（多半又是一个换行，然后一个新的 `def`），而评测只取第一个换行之前的文字，于是答案成了空的。

证据来自只读的诊断脚本（没有运行任何模型写的代码）：把提示和"提示加标准答案"分别分词，在边界之前的 token 完全一样的，500 道抽样填空题里是 0 道，500 道抽样 RepoBench 题里是 47 道（这 500 道 RepoBench 的标准答案里 454 道是带缩进的）。在 60 道填空题上，task 阶段的模型有 53 道（FIM 模式）和 34 道（仅前缀模式）直接答了空字符串。

另外做了一个**诊断**，方法和上面的表不同，不是官方记录，也不在表里：把提示末尾的换行拿掉，让模型自己写出"换行加缩进"那个 token，再取第一行非空内容。只在同样抽样的前 100 题上做：

| 阶段 | 项目 | 表里的方法 | 诊断的方法 |
|---|---|---|---|
| task | 填空（仅前缀）答对 | 2 / 100 | 9 / 100 |
| task | RepoBench EM | 3 / 100 | 10 / 100 |
| task | RepoBench ES | 26.4 | 49.6 |
| stage2 | 填空（仅前缀）答对 | 1 / 100 | 7 / 100 |
| stage2 | RepoBench EM | 3 / 100 | 13 / 100 |
| stage2 | RepoBench ES | 25.7 | 51.4 |

这说明表里黑米的代码数字被评测方式压低了很多。还没有做的事：GPT-2 的分词器有没有同样的毛病（可能程度轻一些）没有查；修正后的方法要同时用在两个模型上、两边都重新评完，代码列才能互相比，这件事没做，要不要做由你决定。另外还有一件没弄明白的事：task 阶段的 FIM 模式比仅前缀模式答空的还多，项目自己的"样本墙"里 task 阶段也有"（什么都没写）"。task 阶段的填空训练是不是按预期起了作用，没有调查。

结论：三个标准任务的列可以信；这张表里的四个代码列，对黑米来说只能当作"至少有这么多"，不要据此得出"黑米写代码不如 GPT-2"。

**2. 黑米可能见过一部分考题，GPT-2 不可能见过。**

黑米的通用文本是 `HuggingFaceFW/fineweb-edu`（网页），代码来自 `codeparrot/github-code-clean`（GitHub 上的代码，见 `docs/data/report.md`）。WikiText-2 是维基百科的文章，HumanEval 的题目 2021 年起就公开在 GitHub 上，所以这两样都可能混在黑米的训练数据里。GPT-2（2019 年）用的 WebText 数据里特意去掉了维基百科，而且它比 HumanEval 还早。

这件事**没有量过**，没有做过重合检查。在检查之前，黑米的 WikiText 和单行填空数字相对 GPT-2 可能偏好看。程度不知道，这里不估。

**3. 哪些数字是官方的。**

BLiMP、HellaSwag、WikiText 是官方评测，框架原样运行。RepoBench 是官方的数据和提示，但只用 `in_file`、贪心解码、抽 500 题、ES 是自己重写的公式。单行填空是一字不差的比例，不是官方的 pass@1，只是它的下界，因为这里从不运行模型写出来的代码。这些数字只能和表里的 GPT-2 比，不能和论文、排行榜比。

**4. 运行时的注意事项，以及一个没核实的东西。**

- 训练在跑时命令拒绝在显卡上开始，是因为 Windows 上显存不够不会报错，而是悄悄挤到系统内存里，评测和训练两边都会慢得像爬。三条出路见上面"训练在跑的时候怎么办"。评 GPT-2 全量时显存最高用到约 15.4 GB（显卡共 16.3 GB），已经贴着那条线，所以评参照时不要同时开游戏或训练。
- 记录按检查点的**文件名**记。你重新训练出一个同名的检查点，命令会以为评过了而跳过，要加 `--force` 才会重评。
- 只评一部分题的 GPT-2（`--reference gpt2 --limit N`）不会覆盖参照文件里已有的更完整结果，命令会拒绝。想覆盖加 `--force`，想另存加 `--reference-out 别的路径`。
- 设计说明里给 GPT-2 标的合理范围（BLiMP 0.75 以上、HellaSwag `acc_norm` 在 0.28 到 0.34、WikiText word perplexity 在 30 到 45）是凭记忆写的，没有逐一核实，只用来发现明显的环境错误，不是验收线。这次三个数都落在范围里（0.8215、0.3114、37.37）。
