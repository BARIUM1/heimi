机器：RTX 5080 笔记本版，16 GB 显存；torch 2.11.0+cu128；Windows 11。

## 三个结论

**1. Windows 上显存超限不报错，而是溢出到系统内存，速度掉一到两个数量级。**
级 0 微批 32 的 allocated 峰值 14.08 GB 看似没满，吞吐却从 228k 掉到 79k（每步 415 ms，线性外推应为 144 ms），说明已经在溢出；微批 64 用到 27.8 GB，吞吐只剩 5.4k。CUDA 不抛 OutOfMemoryError。因此训练必须自己守住峰值显存，而且要看驱动实际持有的 reserved 而不是 allocated（allocated 会低估）。脚本现在在第一步后检查峰值 reserved 是否超过物理显存的 80%（本机 17.07 GB 的 80% 约 13.7 GB），超过即判定溢出退出；守卫逻辑在 `minids/memguard.py`，计划三的训练循环直接复用。

**2. 显存主要被 logits 占掉。**
词表 16384 乘序列 1024，每条序列的 logits 在 fp32 下就是 64 MB，再加交叉熵的中间量，微批 16 时仅这一项就超过 3 GB。这解释了为什么 13M 的模型也能吃掉 14 GB。微批次因此被 logits 而不是模型大小限制。计划三若需要更大微批，可用分块交叉熵；本期不做。

**3. `torch.compile` 在本机 Windows 环境不可用，已按设计回退普通模式。**
失败原因是 `TritonMissing`：官方 Windows 版 torch 不带 Triton，inductor 后端生成不了 GPU 内核。首次前向失败后脚本自动重建普通模型继续，吞吐与不开 compile 一致。训练循环沿用"尝试、失败即回退"的策略，不依赖它。社区有 `triton-windows` 包可装，预计能提速 20% 到 40%，留作以后的可选优化，本期不装。

## 对 spec 8.1 时间预算的修正

按推荐微批次的实测吞吐换算：

| 阶段 | token 预算 | 实测 tokens/s | 预计耗时 |
|---|---|---|---|
| 级 0 | 0.3B | 228k | 约 22 分钟 |
| 级 1 | 0.5B | 133k | 约 1.0 小时 |
| 级 2 | 2.0B | 52.5k | 约 10.6 小时 |
| 任务阶段 | 0.7B | 52.5k | 约 3.7 小时 |
| 对照组 | 2.0B | 52.5k | 约 10.6 小时 |
| 合计 | 5.5B | | 约 26 小时 |

级 2 的 2.0B 预算需要 10.6 小时，低于 spec 第 16 节设定的 14 小时阈值，预算维持 2.0B 不变。spec 第 15 节"约 27 小时"的估计成立。实际训练还有数据加载、评测、检查点写入的开销，按 10% 到 15% 计，总计约 29 到 30 小时，分三个夜晚。
