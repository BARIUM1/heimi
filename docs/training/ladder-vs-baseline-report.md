# 阶梯与对照组对比报告（2026-11-11）

机器：RTX 5080 笔记本版 16 GB，torch 2.11.0+cu128，Windows 11。代码：master `668901f`（stage1、stage2、task 和对照组的最终检查点记录的都是这个提交；stage0 是 2026-11-09 中午在更早的提交 `ab69181` 上训练的）。
数据：`data/tokens/`（web 6.58B / code 1.17B 训练 token），分词器 `data/tokenizer/heimi-16k.json`，种子 1337。
两个 run 各跑了一次。`runs/` 不进 git，本报告里的数字就是留档。

2026-11-24 补充：对照组接上 task 阶段、再做官方评测的结果，在文末"补充"一节。正文是 2026-11-11 的原文，只在"后续可做"里标了两条已做。

## 结论

1. **spec 1.3 第 2 条没有达到。** 对照组（16 层 d768，从零训练 2.0B token）最终验证损失 web 3.0717 / code 1.3905。阶梯在预训练结束时（stage2 末，累计 2.80B token）是 web 3.1525 / code 1.5478，全程没有降到对照组的最终损失。
2. **同样的级 2 预算，长大来的起点不如随机起点。** stage2 与对照组的结构、token 预算、学习率、预热、数据配比都相同，只差初始化。阶梯多花了 0.80B token 训练小模型，最终反而差 0.081（web）和 0.157（code）。
3. **达到同一 web 损失，阶梯需要约 2.0 倍的 token**；按纯训练时间算是 1.2 到 1.6 倍。只有最初约 2.4 小时阶梯领先，因为小模型每步更快。
4. 其余四条成功标准达到，见"成功标准逐条"。

## 观察

1. **加宽之后学得慢。** stage2 的头 500 步（262M token）web 只降了 0.034（3.5704 → 3.5364）。对照组在相近的损失水平上（3.5181 → 3.3471），同样 262M token 降了 0.171。
2. **HellaSwag 分不出高下。** 对照组 2,740 题，阶梯 2,674 题，差 66 题（0.0066）。单个正确率的标准误约 0.0044，两者之差的标准误约 0.0063，差距约 1 个标准误。两者都只比随机（25%）高 2 个百分点左右。
3. **task 阶段按预期工作。** 数据配比换成 code 80% 后，code 损失从 1.5478 降到 1.2099，web 从 3.1525 回升到 3.2024，FIM 精确匹配从 0.001 升到 0.036。`task_final.pt` 是唯一学过 FIM 格式的检查点。
4. **吞吐高于基准预测。** stage2 与对照组中位数都是 59.0k tok/s，`docs/benchmarks/throughput.md` 的预测是 52.5k。
5. **进入新一级时优化器是新建的**（`minids/train/loop.py` 的 `_enter_stage`），AdamW 的动量状态不从上一级继承，并且重新预热 5%。

## 可能的原因（都没有验证）

以下是猜测，各自对应一个能检验它的实验，本期都没做。

1. **克隆出来的神经元分不开。** 加宽把每个神经元复制一份，只在新矩阵上加了相对 1e-3 的噪声（`noise_std_rel`）。如果两份长期保持几乎相同，新增的宽度就没有变成有效容量。检验：统计 stage2 各检查点里成对神经元权重的相似度；或换更大的噪声重跑。
2. **小模型的解不是宽模型的好起点。** 小模型用有限容量学到的表示，宽模型可能要先"改掉"才能学得更好。检验：对照组第 1,500 步之后与 stage2 同步数的检查点做表示相似度比较。
3. **进入级 2 时丢了优化器状态并重新预热。** 检验：加宽时把 AdamW 状态一并映射过去，或去掉预热重跑前 500 步。
4. **级 2 的学习率是为从零训练选的。** 长大来的模型可能需要不同的学习率。检验：stage2 前 500 步的学习率扫描。

## 局限

- 两个 run 各只跑了一次，同一个种子。没有测过种子之间的波动有多大；不过在"逐步对齐"的比较里，从第 2,000 步起的每个评测点、两个验证语料上，对照组都领先，方向一致。
- 加宽的噪声、各级学习率、三级之间的 token 分配（0.3B / 0.5B / 2.0B）都没有调过。结论是"这套设置下长大没有省数据"，不是"长大这个方法无效"。
- 只在 1.03 亿参数、2.0B token 这个规模上做了实验。
- 时间是笔记本上的纯训练时间，训练期间有别的桌面程序在用 GPU。
- 评测点每 500 步一个，"达到同一损失"的位置是线性插值。

### 怎么读

1. **预训练的差距带到了 task 阶段之后。** task 末对照组的验证损失是 web 3.1157 / code 1.1078，阶梯是 3.2024 / 1.2099，差 0.087 和 0.102（进入 task 前差 0.081 和 0.157）。对照组少用 0.80B token，纯训练时间少 1.48 小时。
2. **三项标准任务方向相同。** task 末对照组对阶梯：BLiMP 0.7580 对 0.7438，bits/byte 1.1450 对 1.1731，HellaSwag acc_norm 0.2868 对 0.2807。BLiMP 的差距（0.014）按 67,000 道题互相独立粗算约 6 个标准误；HellaSwag 的差距约 1 个标准误，分不出高下（训练自带的 HellaSwag 也是：2,733 对 2,674 题，不到 1 个标准误）。
3. **"接着写下一行"的两项，对照组的数字更高，但在抽样误差之内。** RepoBench EM 0.116 对 0.100（500 题里 58 对 50 题），ES 56.47 对 55.12，仅前缀填空 0.116 对 0.096（58 对 48 题）。两个比例之差的标准误约 0.02，两项差距都在 1 个标准误上下。
4. **填空（FIM）是阶梯更高，两把尺子都是。** 训练自带评测 1,000 题：阶梯 36 题，对照组 18 题。官方单行填空 500 题：阶梯 14 题（0.028），对照组 6 题（0.012）。按两个独立比例粗算，差距分别约 2.5 和 1.8 个标准误；两把尺子的题目来源不同，方向一致。原因没有查。
5. **所以 11-11 写下的预期只对了一半。** "对照组得到更好的代码补全模型"在 FIM 上不成立；在"接着写下一行"上，数字偏向对照组，但没有超出误差。验证损失更低，没有换来更高的填空命中率。
6. **两个模型的 FIM 都远低于仅前缀**（对照组 0.012 对 0.116，阶梯 0.028 对 0.096）。`docs/official-eval.md` "要小心的地方"第 5 条那个没查清的问题，在对照组上同样存在，而且更明显。在它查清之前，第 4 条的差距只当作观察记录，不当作"阶梯更会填空"的结论。
7. **task 阶段对通用英文的代价，两边接近。** web 验证损失上升：对照组 0.044，阶梯 0.050。bits/byte 上升：0.0155 对 0.0163。BLiMP 下降：对照组 0.0037（0.7617 → 0.7580），阶梯 0.0115（0.7553 → 0.7438）。
8. **预训练结束时，RepoBench 是阶梯略高**（EM 0.098 对 0.090，ES 55.00 对 53.22），尽管对照组的 code 验证损失更低（1.3905 对 1.5478）。EM 的差距不到 1 个标准误；ES 没有估过误差。
9. spec 1.3 第 2 条的结论不变，那一条说的是预训练。这次补充的是：加上 task 阶段之后，用更少 token 得到更低验证损失的仍然是对照组。

### 这次补充的局限

- 仍然是每个 run 一次、同一个种子。
- 两个 run 在 task 阶段读到的训练窗口不同。数据顺序由跨级累计的微步数决定：进入 task 时阶梯是 292,896，对照组是 244,096（检查点里的 `micro_step`）。分布相同，具体窗口不同。
- 对照组的 task 阶段中断过一次，阶梯的没有。
- 对照组和阶梯的官方评测不是同一天测的。
- FIM 的差距没有做配对比较（同一批题上各自答对了哪些，没有交叉统计），上面的标准误是按独立样本粗算的。
- 黑米可能见过一部分考题（`docs/official-eval.md` 第二次实测"要小心的地方"第 2 条）。两个 run 的训练数据来源相同，这一点不影响两者互比，但影响和 GPT-2 比。
